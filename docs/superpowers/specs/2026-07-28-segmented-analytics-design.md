# 세그먼트 분석 플랫폼 설계 (큐브 기반 재설계)

작성일: 2026-07-28

## 배경

기존 설계(`2026-07-22-data-layer-design.md`, `2026-07-22-skill-platform-contract-design.md`,
`2026-07-23-descriptive-analytics-design.md`)는 식별 테이블 `all_tiara_i` 위에서
표본 캐시 + 요청형 절대지표를 전제했다. 두 가지가 바뀌어 원점 재설계가 필요해졌다.

1. **데이터 원천 교체** — 추정 성·연령 데이터와 조인하기 위해 비식별 테이블 `all_tiara_n`
   으로 이동. 유저·세션 식별자가 `app_user_id`/`isuid` → `uuid`/`suid` 로 전면 교체된다.
2. **목표 확장** — 마르코프 분석(기존 노트북)과 기술통계(UV/PV/세션)를 **같은 구조에서**
   기간·성별·연령대·앱버전 세그먼트로 뽑는 것이 목표다.

## 목표와 비목표

**목표**
- 마르코프 분석과 기술통계를 하나의 재료 파이프라인에서 산출해 숫자가 어긋나지 않게 한다.
- 기간·성별·연령대·앱버전·OS·시간대·서비스타입 세그먼트를 **서버 재질의 없이** 탐색한다.
- 전수(전 인구) 집계를 유지한다. 표본을 쓰지 않는다.
- 로그 구현 편차를 측정 가능한 형태로 드러낸다.

**비목표**
- 다수 사용자용 웹 서비스. 사용자는 1인(향후 소수 동료)이며 로컬 대시보드로 충분하다.
- 개별 유저 단위 추적. 큐브는 집계값만 보유한다.
- 실시간성. 일 단위 배치로 충분하다.

## 확정된 설계 결정

| # | 결정 | 근거 |
|---|---|---|
| 1 | **전수 집계**. 표본 경로 폐기 | 마르코프 지표는 전이 카운트만 필요하므로 서버 집계 후 작은 큐브만 내리면 전수가 가능 |
| 2 | **사전집계 큐브(C안)** | 전수 유지 + 로컬 탐색 즉시성을 동시에 만족하는 유일한 구조 |
| 3 | **세션키 = `(uuid, suid)` 쌍** | `suid` 단독은 0.1% 중복 (11,835,195 vs 11,846,564) |
| 4 | **분석 범위 = 앱 전체 여정** (서비스 가로지름) | 세션 42.4%가 2개 이상 서비스에 걸침 |
| 5 | **계층 state** `service_code / 화면` | 서비스별 화면 해상도 편차(media 100종 vs content_v 3종)를 롤업으로 흡수 |
| 6 | **2층 구조** (화면층 × 행동층) | 화면 이동과 화면 내 행동을 분리해야 전이 해석이 명확해지고 버전 비교에서 원인이 분리됨 |
| 7 | **state 매핑 완전 자동** (커버리지 컷) | 수작업 매핑 폐기. 컷 규칙만 버전 관리 |
| 8 | **앱버전은 인접 쌍 델타 비교** | 여러 버전 동시 비교는 불필요 |
| 9 | **성연령은 매칭분 한정 경향성 분석** | 전수 보존 강박 없음. 단 `unknown` 버킷은 보존 |
| 10 | **결과 = 요청형 + 표준 리포트 팩 병행** | 평소 탐색은 대시보드, 정리는 팩 |

## state 정의

### 화면층 (Level 0 / Level 1)

```
state = "{service_code}/{화면명}"        예: top/홈탭_진입, media/뉴스뷰
        + 특수 상태 START, EXIT
```

- **화면 신호 = `action.type='Pageview'` 의 `action.name`**.
- `action.type='Usage'` + `kind='UsagePage'` 는 화면 신호가 아니라 **체류시간 귀속용**으로
  쓴다 (`action.name` 이 Pageview와 동일: `홈탭_진입` 등).
- `common.page` 는 fallback이 **아니고 교차검증용**이다. Pageview일 때
  `action.name ↔ common.page` 대응이 깨지는 비율을 `quality` 큐브에 기록한다.
  (측정: `common.page` 를 fallback으로 써도 세션 커버리지는 0.9%p만 증가)
- **커버리지 컷**: 누적 커버리지 상위 95%까지 채택하고, 그 안에 들어도 기간 전체 건수가
  `min_count`(기본 10,000) 미만이면 제외한다. 제외된 것은 `{service_code}/other` 로
  흡수한다. `cut_ratio`(0.95)와 `min_count`(10,000)는 버전 관리되는 config 값이다.
- **버전 비교 시**: 비교 대상 기간·버전을 **합쳐서 컷을 한 번만** 적용해 공통 state
  집합을 고정한다. 버전별로 따로 컷하면 state 집합이 달라져 전이행렬 비교가 깨진다.

### 행동층 (Level 0 / 1 / 2)

```
action_key = action_kind / click_layer1 / click_layer2
             ClickContent / home_main   / FEED_SLOT_ISSUE
```

- `action.kind` 8종 규모 (`ClickContent`, `ViewContentList`, `Search`, `Share`,
  `AppLaunch`, `AppExit`, `UsagePage`, 기타).
- `click.layer1` 24종, NULL 0.0%. `layer1>layer2` 374종, 3단까지 861종.
- 기존 수작업 `state.csv` 의 `뉴스_1슬롯`·`엔터_2슬롯`·`머니_1슬롯` 등은
  `layer1`/`layer2` 로 자동 표현된다.
- 클릭의 화면 귀속은 `common.page` 로 한다(윈도우 함수 불필요).
  `page × layer1` 대응이 일관됨을 실측 확인.

### 분석 모집단

**화면 이벤트가 1개 이상인 세션(53.3%)** 만 여정 분석 대상이다. 나머지는 광고 요청
(`axzad_request`)·`js_*` 콜만 있는 세션으로 사용자 여정이 아니다. 이 비율은 버리지 않고
모든 결과에 커버리지로 첨부한다.

## 세그먼트 축

**코어 7축 — 전부 교차한다**

| 축 | 값 | 개수 |
|---|---|---|
| `period` | 날짜 (day 단위, 상위는 롤업) | 기간만큼 |
| `service_type` | `MA`(모바일앱) / `MW`(모바일웹) / `PW`(PC웹) | 3 |
| `os` | android / ios / windows / macos / 기타 | 5 |
| `gender` | M / F / N / unknown | 4 |
| `age_band` | 미상 / 10 / 20 / 30 / 40 / 50 / 60 / 70 (`service_age_band`) | 8 |
| `daypart` | 00~05 / 06~11 / 12~17 / 18~23 | 4 |
| `app_version` | 상위 16 + `other` | 17 |

`app_version` 의 "상위 16"은 **큐브 빌드 대상 기간 전체의 이벤트 수 기준**으로 정하며,
state 사전과 함께 1단계에서 확정해 고정한다(날짜별로 다르게 뽑지 않는다).

`service_type` 은 필수다. 실측 트래픽이 `MW` 21.4억 / `PW` 9.3억 / `MA` 5.5억 로
웹이 대부분이며, 앱·모바일웹·PC웹을 한 전이행렬에 섞으면 여정 해석이 무의미해진다.

**축에서 제외한 것**

| 제외 | 이유 |
|---|---|
| 신규/기존 유저 (`app_install_date`) | 30.8억 행 NULL — 데이터 없음 |
| A/B 실험 (`bucket.experiment_key`) | 1종 14행, 미사용 |
| 국가 / `deployment` | 전부 NULL 또는 단일값 |
| `network_state` | NULL 30.7억, 앱에서만 유효 |
| 기기모델 / OS버전 | 코어에 넣으면 하루 21만 → 113만 행으로 5배 증가. 필요 시 재집계 |

## 큐브 스키마 (6종)

| # | 큐브 | 키 | 값 | 크기/일 |
|---|---|---|---|---|
| ① | `session` | 7축 + GROUPING SETS 롤업행 | `sessions`, `uv`, `pv`, `events`, `duration_sum` | 수천 |
| ② | `transition` | 7축 + `from_state` + `to_state` | `cnt`, `dur_sum` | 214,368 (실측) |
| ③ | `action` | 7축 + `screen` + `action_kind` + `click_layer1` + `click_layer2` | `cnt` | 수천 |
| ④ | `cond_transition` | 4축(`period`,`service_type`,`os`,`app_version`) + `from_state` + `action_kind` + `to_state` | `cnt` | ~6만 (추정) |
| ⑤ | `path` | 7축 + `n`(3~5) + `path` — 세그먼트×n 당 상위 200 | `cnt` | 제한적 |
| ⑥ | `quality` | `period` + `service_code` + `app_version` + `check_name` | `violated`, `total`, `ratio` | 수백 |

30일 전체 합산 1,000만 행 남짓, parquet 수백 MB 이내.

④는 축을 4개로 줄였다. 7축을 모두 쓰면 하루 최대 171만 행(전이쌍 3,604 × kind 8)이 되어
코어보다 무거워진다. "어떤 행동이 다음 화면을 결정하는가"를 성별·연령까지 쪼개 볼
필요는 낮다고 판단했다.

### uv 비가산 처리 (중요)

`cnt`·`sessions`·`pv` 는 가산이라 롤업이 자유롭다. **`uv` 는 가산이 아니다** —
같은 유저가 이틀 방문하면 1이지 2가 아니다. 단순 합산하면 UV가 부풀어 기술통계의
핵심 지표가 조용히 틀린다.

대응:
1. `session` 큐브를 `GROUPING SETS` 로 생성해 축별 `ALL` 롤업 행을 미리 계산한다.
   (`session` 큐브는 수천 행 규모라 부풀려도 부담이 없다)
2. **클라이언트는 `uv` 를 절대 합산하지 않는다**를 규칙으로 강제한다.
3. 큐브에 없는 롤업 조합은 요청 시 거부하고, 대시보드에서는 선택 자체를 막는다.

## 데이터 정합성 5원칙

실측된 로그 구현 편차 (2026-07-27, android):

| 서비스 | 행수 | Pageview 비율 | `action.name` NULL | Pageview 이름 종수 |
|---|---|---|---|---|
| `top` | 11.0억 | 11.0% | 19.8% | 21 |
| `media` | 7.5억 | 4.6% | 5.1% | 100 |
| `entertain` | 2.0억 | 5.0% | 5.3% | 8 |
| `sports` | 1.5억 | 5.4% | 5.2% | 6 |
| `content_v` | 1.5억 | 3.3% | 3.3% | 3 |
| `search` | 0.3억 | 64.0% | 0.0% | 1 |

그 외: `Pageview` 인데 `kind=ViewContentList` 가 Pageview의 65%(3,248만).

**① 분석 범위를 로그 품질로 정의한다** — 범위를 좁히는 것이 정확도를 사는 방법이다.
서비스 묶음을 명시하고 그 안에서만 전이를 말한다.

**② 품질 검증을 파이프라인 1급 단계로 승격한다** — 매 실행 자동 실행 + 결과 동봉.
검사 항목: Pageview 없는 세션 비율 / NULL `action.name` 비율 / `type×kind` 모순 조합 /
`action.name ↔ common.page` 불일치 / 신규 state 유입 / 버전 간 state 집합 변동.

**③ 단일 신호에 의존하지 않고 삼각측량한다** — 화면 판정을 `Pageview` 하나로만 하되,
`common.page` 와의 불일치율을 지표로 만들어 감시한다.

**④ 의심 데이터를 조용히 버리지 않는다** — `unknown` 을 명시 상태로 남기고 커버리지를
모든 결과에 첨부한다.

**⑤ 절대값이 아니라 델타로 읽는다** — 로그가 부정확해도 편향이 두 버전에 동일하게
작용하면 델타는 유효하다. 단 "버전 간 로깅 자체가 바뀐 경우"를 검출하는 검사(②)가
반드시 짝으로 있어야 한다. 없으면 로깅 변경을 행동 변화로 오독한다.

인접 버전 안정성 실측: 9.5.0 vs 9.5.1 의 상위 95% `action.name` 집합이 각 24종 중
23종 공통(≈96% 겹침). 롱테일에서만 신규가 발생하며 `other` 로 흡수 가능하다.

## 컴포넌트 경계

```
data_layer/        기존. Trino 접속·SQL 실행·parquet 캐시·매니페스트
analytics/
  cube/            큐브 정의와 집계 SQL 생성
  metrics/
    markov.py      P행렬·stationary·expected steps·absorption·PMI·이탈확률
    descriptive.py UV·PV·세션·체류시간
    paths.py       n-gram 경로
    quality.py     정합성 검사
  report/          표준 리포트 팩 (HTML)
dashboard/         로컬 뷰어
.claude/skills/    Claude 스킬 진입점 (얇은 껍데기)
```

**경계 규칙**

1. **`metrics/` 는 DB를 모른다.** 입력은 큐브(DataFrame), 출력은 지표(DataFrame)인
   순수 함수다. Trino 없이 손으로 만든 작은 큐브로 검증할 수 있어야 한다.
   마르코프 수식 버그는 그럴듯한 숫자를 내므로 이 격리가 필수다.
2. **계산 로직은 `metrics/` 에만 존재한다.** 대시보드가 `metrics/` 를 호출해 그 자리에서
   계산하는 것은 허용된다(같은 코드이므로 숫자가 어긋날 수 없다). 대시보드가 자체
   계산 로직을 갖는 것은 금지한다.
3. **분석 단계는 Trino에 접근하지 않는다.** 큐브가 없으면 실패하고, 몰래 서버로
   폴백하지 않는다.
4. `skills/descriptive/` 는 `analytics/metrics/descriptive.py` 로 흡수한다.

## 데이터 흐름

### 큐브 빌드는 2단계다

state 컷은 기간 전체를 봐야 정해지지만 큐브는 날짜별 증분 저장이 필요하다. 이 충돌을
state 사전을 먼저 고정하는 방식으로 해소한다.

```
[1단계] state 사전 생성 — 기간 전체 1회, 가벼운 집계 (전이 없음)
   → 화면·클릭레이어별 건수 집계 → 상위 95% 컷 → 나머지 other
   → cache/state_dicts/{해시}.json
      { "version": "sd_...", "screens": [...], "layer1": [...], "cut": 0.95 }

[2단계] 큐브 빌드 — 날짜별, state 사전 고정
   for day in 기간:
     (day, state_dict_version, axes) 가 캐시에 있으면 건너뜀
     없으면 Trino 집계 → cache/cubes/{큐브}/date={day}.parquet → 매니페스트 등록
```

### 세션 귀속과 날짜 경계

세션은 자정을 넘을 수 있으므로 날짜별 독립 빌드가 그대로는 성립하지 않는다. 기존
data_layer의 "개체-완결" 규칙을 큐브에도 적용한다.

- **세션은 첫 이벤트 날짜에 귀속한다.** 축 값도 첫 이벤트 기준(`min_by(expr, ts)`)이다.
  따라서 세션 하나가 날짜·버전·시간대 축에서 쪼개지지 않는다.
- 날짜 `D` 의 큐브를 빌드할 때 **`date_id IN (D-1, D, D+1)` 세 파티션**을 읽고
  **첫 이벤트가 `D` 인 세션만** 채택한다.

  `D+1` 은 `D` 에 시작해 자정을 넘긴 세션의 꼬리를 확보하기 위한 것이고,
  **`D-1` 은 중복 집계를 막기 위한 것이다.** `D-1` 을 읽지 않으면 `D-1` 23:50에 시작해
  `D` 00:10까지 이어진 세션이 두 번 집계된다 — `D-1` 빌드는 온전히 집계하고, `D` 빌드는
  자기 창 밖의 첫 이벤트를 **볼 수 없어서** 꼬리를 "`D` 에 시작한 세션"으로 정당하게
  판정한다. `sessions`·`uv`·`events`·`pv` 가 모두 부푼다. `D-1` 을 읽으면 `D` 빌드가 첫
  이벤트를 보게 되어 `min(ts)` 날짜가 `D-1` 이 되고 정확히 배제된다.

- **잔여 한계(실측으로 크기 확인됨)**: 3일 이상에 걸친 세션은 두 경우로 갈린다.
  - 날짜가 **연속**이면(`D-1, D, D+1` 모두 이벤트 있음) 첫 날짜 빌드가 한 번만 집계하고
    뒤쪽이 절단된다. 중복이 아니라 절단이므로 허용한다.
  - 날짜에 **구멍**이 있으면(`D-1` 과 `D+1` 에만 있고 `D` 에는 없음) `D-1` 빌드와 `D+1`
    빌드가 각자 상대의 이벤트를 못 보고 **양쪽에서 집계된다.** 이건 중복이다.

  실측(2026-07-26~28, `weather`, 890,062 세션): span>30분 13,399(1.5%),
  span>6시간 1,305(0.15%), span>24시간 82(0.009%), **구멍 난 세션 2개(0.0002%)**.
  최대 span은 61.5시간. 즉 중복 노출은 890,062 중 2건이다.

  이 크기 때문에 세션 SQL을 더 복잡하게 만들지 않고 **감시 대상으로 둔다**: `quality`
  큐브에 `session_span_exceeds_timeout` 검사를 넣어 타임아웃 계약을 위반하는 세션 비율을
  상시 측정한다. 이 비율이 유의미하게 커지면(예: 오프라인 큐잉·백필 유입, `suid` 재사용)
  세션 span 상한으로 배제하는 구조적 수정을 검토한다.

- `date_id` 와 `date(access_time)` 의 정합성은 실측 확인됨: `date_id='2026-07-27'` 파티션의
  1,439,045행 전부가 `access_time` 날짜도 2026-07-27이다. 타임존 경계 불일치는 없다.
- 비용은 하루당 3개 날짜 파티션 스캔이다. 파티션 프루닝이 적용되므로 전체 스캔에 비해
  무시할 수 있다.
- **검증**: Task 14에서 날짜별 빌드의 `sessions` 합계를 기간 전체 단일 집계와 대조한다.
  이 종류의 오류는 문자열 테스트로 잡히지 않고 실데이터 대조로만 드러난다.

### 캐시 키

```
cube_key = hash(source_version, state_dict_version, axes, cube_name, date)
```

하나라도 바뀌면 다른 파일이 된다. 조용한 덮어쓰기가 구조적으로 불가능하다.

### 서버 잔여물 없음

큐브 집계는 CTE 단일 `SELECT` 로 수행하며 서버에 테이블을 만들지 않는다
(실측 검증됨). 표본 경로 전용인 `TrinoEventFetcher`·`build_prepare_sql`·`cleanup.py`
는 삭제한다. 삭제하면 "그룹 계정 하위에 데이터를 남기지 말라"는 데이터허브 제약을
구조적으로 지키게 된다.

### 분석 흐름

```
요청 → analytics/metrics
   ① cache/cubes/{큐브}/date=* 읽기 (DuckDB)
   ② 세그먼트 WHERE 필터
   ③ 지표 계산
   ④ publish_result(결과 + viz힌트 + 커버리지 + 품질경고)
```

### 결과에 항상 동봉하는 것

| 항목 | 예 |
|---|---|
| 커버리지 | "화면 있는 세션 53.3% 기준" |
| 성연령 매칭률 | "연령 유효 64.7%, unknown 제외됨" |
| 품질 경고 | "top 서비스 NULL action.name 19.8%" |
| state 사전 버전 | `sd_a1b2c3` |
| 비교 안전성 | "9.5.0↔9.5.1 state 집합 96% 일치 — 비교 가능" |

### 결과 생성 방식

- **요청형(기본)**: 대시보드에서 세그먼트·분석을 고르면 그 자리에서 계산해 렌더한다.
  큐브가 있으면 마르코프 계산은 밀리초이므로 미리 생성할 이유가 없다.
- **표준 리포트 팩**: "버전 비교 리포트" 등을 HTML 한 장으로 산출한다.
  구성: UV/PV/세션/체류 변화 · 전이 히트맵 델타 · 전이확률 변화 Top20 ·
  stationary 변화 · 이탈률 변화 Top10 · 화면별 클릭 분포 변화 · 경로 n-gram 변화 ·
  품질 경고와 커버리지.

## 실패 처리

| 실패 | 처리 |
|---|---|
| 쿼리가 안 끝남 | 타임아웃(기본 10분) → 취소 + "기간을 줄이거나 서비스를 좁히세요" |
| 파티션 프루닝 누락 | `date_id`·`c_service_code` 조건이 없으면 **실행 전 거부** |
| 날짜 일부 실패 | 성공분만 커밋, 실패 날짜는 미등록 → 재실행 시 실패분만 재시도 |
| 권한 없음 | `PERMISSION_DENIED` 를 테이블명과 함께 그대로 노출 |
| 크레덴셜 없음 | 실행 전 검사, 값은 로그에 남기지 않음 |
| 큐브 없이 분석 요청 | 실패. Trino로 폴백하지 않음 |
| state 사전 버전 불일치 | 서로 다른 버전의 큐브를 섞어 계산하려 하면 거부 |
| `uv` 합산 시도 | 큐브에 없는 롤업 조합 요청은 거부 |
| 빈 결과 | 에러가 아님. "해당 세그먼트 데이터 없음"을 명시해 발행 |
| 품질 임계 초과 | 막지 않고 경고를 결과에 첨부 |

**두 원칙**

1. **조용한 실패를 만들지 않는다.** 탐색 중 `NOT IN` 이 NULL 때문에 0을 반환해
   잘못된 결론에 이를 뻔했다. SQL 작성 규약으로 `NOT IN` 을 금지하고
   `NOT EXISTS`/`LEFT JOIN` 을 쓴다. NULL 비율은 `quality` 큐브에서 상시 감시한다.
2. **막을 것과 경고할 것을 구분한다.** 계산이 틀리게 되는 것(uv 합산, state 버전 혼합,
   프루닝 누락)은 막는다. 해석에 주의가 필요한 것(커버리지·매칭률·로깅 편차)은
   정보를 주고 통과시킨다.

## 테스트 전략

**`metrics/`** — 순수 함수이므로 가장 엄격하게. Trino 없이 밀리초에 돈다.
- 해석적 정답: 2~3 상태 소형 체인의 `expected steps to exit`, `absorption prob` 를
  손계산 값과 대조
- 불변식: 전이확률 행 합 = 1 / `π = πP` / absorption 확률 합 = 1 / expected steps > 0
- 속성 기반: 무작위 체인 생성 후 위 불변식 검증

**`cube/`** — SQL 빌더 문자열 검증
- `date_id`·`c_service_code` 조건이 반드시 포함되는지 (프루닝 강제)
- `NOT IN` 이 등장하지 않는지
- 축 변경이 GROUP BY에 반영되는지
- state 사전 변경이 캐시 키를 바꾸는지

**`data_layer/`** — 기존 87개 테스트를 회귀 가드로 유지한다.

**라이브 통합** — 크레덴셜이 있을 때만 실행(`tests/integration/` 기존 패턴).
하루치 소형 큐브를 실제로 빌드해 행수·스키마를 검증한다.

**`dashboard/`** — 결과 계약 준수만 검증. 계산 로직이 없으므로 테스트할 로직도 없다.

**노트북 대조** — 완전 일치는 불가능하다(DB·식별자·모수·state 정의가 모두 바뀜).
숫자 일치가 아니라 구조 일치를 본다: 상위 전이 20개의 순위 상관(Spearman),
이탈률 상위 state 집합의 겹침, stationary 상위 hub state 일치. 정답 검증이 아니라
이상 감지 용도다.

**회귀 방지** — 큐브 파일에 스키마 버전을 넣고 읽을 때 검증한다.

## 구현 단계 분해

이 설계는 하나의 구현 계획으로 담기에 크다. 아래 4단계로 나누고 **각 단계가 독립된
계획(plan) → 구현 → 리뷰 사이클**을 갖는다. 단계마다 끝에 쓸 수 있는 결과물이 나온다.

| 단계 | 내용 | 완료 시 얻는 것 |
|---|---|---|
| **1. 원천 이전 + 재료 파이프라인** | `sources.json` 재작성, 하드코딩 제거, 세션키 `(uuid,suid)` 전환, 표본 경로 삭제, state 사전 생성, `session`·`transition`·`quality` 큐브 빌드 | 전수 큐브가 로컬에 생기고 품질 리포트가 나온다 |
| **2. 지표 계산** | `metrics/descriptive.py`(UV/PV/세션/체류), `metrics/markov.py`(P행렬·stationary·이탈·expected steps·absorption·PMI) | 세그먼트별 기술통계와 마르코프 지표를 뽑을 수 있다 |
| **3. 행동층** | `action`·`cond_transition`·`path` 큐브, `metrics/paths.py` | 클릭 분포·조건부 전이·경로 n-gram이 나온다 |
| **4. 표현** | 로컬 대시보드, 표준 리포트 팩(HTML) | 눈으로 탐색하고 리포트를 한 방에 뽑는다 |

**1단계가 가장 위험하고 가장 중요하다.** 원천 교체·식별자 전환·기존 87 테스트 회귀가
모두 여기 걸려 있다. 1단계를 끝내고 실 데이터로 검증한 뒤 2단계로 넘어간다.

## Phase 2 필수 조건 (큐브 소비 규칙)

`analytics/cube/store.read_cube` 는 요청 날짜가 **전부** 없으면 `CubeNotBuiltError` 를 내지만,
**일부만 없으면 있는 것만 조용히 읽는다**(부분 빌드 상태에서도 읽을 수 있어야 하므로 의도된
동작이다). 그래서 30일을 요청해 3일치를 받은 호출자는 **틀린 분모로 계산한 정상적인 답**을
아무 신호 없이 얻는다.

따라서 Phase 2의 `metrics/` 는 비율·평균·확률을 계산하기 전에 **요청 날짜와 실제 읽힌 날짜를
반드시 대조**해야 한다(`has_cube` 로 확인). 이는 권고가 아니라 요건이다. 대조 없이 계산한
결과는 발행하지 않는다.

## 추적 중인 방법론 리스크

구현 중 리뷰에서 드러난 것으로, 결함은 아니지만 결과 해석에 영향을 준다.

**① state 채택 가중치가 이벤트 행 수다.** stage 1의 네 집계는 모두 `count(*)` 로 채택
여부를 정한다. 봇이나 과활동 유저 한 명이 드문 화면을 채택 집합에 밀어올릴 수 있다.
524억 행 규모에서 세션 그룹핑을 피하려는 의도적 단순화지만, "몇 명이 실제로 쓰는가"와
"몇 행이 찍혔는가"는 다른 신호다. 개선안: 유저/세션 distinct 기준으로 바꾸거나,
`BASE_FILTERS` 에 봇 필터를 추가하거나, 유저당 기여를 상한 처리한다.

**② `Pageview` 중 `action.name` NULL 비율을 아직 모른다.** 측정한 "`top` 의 Pageview
`action.name` 16종"은 `COUNT(DISTINCT)` 이므로 NULL을 세지 않는다. 따라서 `(none)` 화면
버킷이 얼마나 커질지는 미지다. `top` 전체 행의 19.8%가 NULL 이름이라는 별도 측정이 있어
무시할 수준이 아닐 수 있다. Task 14의 실빌드에서 `(none)` 버킷 크기와 `quality` 큐브의
`null_action_name` 을 함께 확인해 판단한다. 버킷을 없애지는 않는다 — 원칙 ④에 따라
드러내는 쪽이 맞다.
