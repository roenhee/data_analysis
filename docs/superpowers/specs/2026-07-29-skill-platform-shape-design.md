# 스킬·플랫폼 형태 설계

**한 줄**: 숫자를 만드는 코드 경로를 하나로 만들고, Claude와 대시보드가 **같은 이름 붙은
분석**을 부르게 한다. 비교는 분석이 아니라 **연산자**이며, 오늘 실측으로 드러난 교란들을
그 연산자 한 곳에 가둔다.

## 왜 이 설계인가 — 근거는 전부 2026-07-29 실측이다

이 설계는 취향이 아니라 **하루 동안 밟은 함정들**에서 나왔다. 같은 질문에 다른 코드가
다른 답을 냈고, 그 답들이 전부 그럴듯했다.

| 밟은 함정 | 틀린 답 | 옳은 답 |
|---|---|---|
| 세션 큐브를 그냥 합산 | 2억 8,909만 세션 | 3,212만 (**9.0배**) |
| `uv` 를 합산 | 1,642만 명 | 959만 (**1.71배**) |
| 버전 델타를 14일 전체로 | **+2.9%** | 겹치는 날짜만 −0.2% |
| 배포 전 테스트 트래픽 포함 | **+2.7%** | 배포일 이후 −0.4% |
| 공휴일을 평일로 분류 | 평일 체류 584.2초 | 602.8초 |
| 체류를 `dur_sum/cnt` 로 | 6.67초 | 10.0초 |

**전부 예외를 던지지 않았다.** 숫자만 보면 멀쩡했다. 그래서 이 설계의 목표는 "편하게
만들기" 가 아니라 **"틀린 숫자가 나올 수 없게 만들기"** 다.

## 층

```
analytics/cube/       재료. Trino 필요, 하루 5분, 6종
analytics/metrics/    순수 프리미티브. DB·config 모름, 밀리초
analytics/analyses/   ★ 새 층. 이름 붙은 분석 + 연산자.
                        가드가 코드에 박히고, 발행을 담당한다
        ↑                          ↑
     Claude                    대시보드
                    ↓
cache/results/        발행물 (parquet + 봉투)
```

`metrics/` 는 지금처럼 순수하게 둔다(파일시스템·config 를 임포트하지 않는 것이 테스트로
고정돼 있다). `analyses/` 가 그 위에서 조합하고, config 를 알고, `publish_result` 를 부른다.

## 경계 규칙

1. **숫자를 만드는 코드는 `analyses/` 뿐이다.** Claude 도 대시보드도 여기를 통과한다.
   같은 코드이므로 두 경로가 다른 답을 낼 수 없다.
2. **Claude 는 계산하지 않는다.** 분석을 고르고, 파라미터를 넣고, 결과를 **말로 해석**한다.
3. **대시보드는 자체 계산 로직을 갖지 않는다.** 같은 분석을 부르고 그린다.
4. **탐색은 자유롭되 발행되지 않는다.** 탐색에서 뭔가 나오면 **분석으로 코드화한 뒤**
   발행한다. 오늘 `compare.py`·`coverage.py`·`calendar.py` 가 정확히 그 경로였다.
5. **모든 발행물에 봉투가 붙는다** — 커버리지, 품질 경고, state 사전 버전, 서비스 범위,
   **실제로 쓰인 날짜**.

## 분석 — 무엇을 재나

지금 큐브로 가능한 것:

| 분석 | 내용 |
|---|---|
| `session_trend` | 기간별 UV·PV·세션·체류. 요일/공휴일 분류 포함 |
| `screen_flow` | 전이확률·이탈률·stationary·기대 걸음·흡수확률·PMI<br>**+ entropy·hhi·top_p·effective_choices·p_exit_within_k·pagerank** |
| `screen_dwell_rank` | 화면별 방문당 체류 + 커버리지 |
| `quality_report` | 검사 8종 추이 |
| `reachability` | `reachability(from_state, to_state, k_max)` → `k` 걸음 안에 도달할 확률.<br>노트북의 "홈 → 뉴스뷰 도달 속도" 가 이 형태였다 |
| `screen_communities` | Louvain 군집. **외부 의존이 붙는 유일한 분석** — `networkx` 필요.<br>그래서 우선순위가 가장 낮다 |

3단계(행동층 큐브) 이후:

| 분석 | 내용 |
|---|---|
| `click_distribution` | 화면 안 클릭 분포 |
| `conditional_flow` | 행동 조건부 다음 화면. **조건 축 = `action_kind` 또는 체류 분위** |
| `path_ranking` | 경로 n-gram 순위 |
| `markov_order_test` | **1차 가정 검정** — `P(C|B)` vs `P(C|A→B)` |

굵은 항목들은 기존 마르코프 노트북에 있었으나 지금 설계에 빠져 있던 것이다
(`entorpy_state_transition_metrics`, `kstep-exit-state_k5`, `stationary_hub_compare` 의
PageRank, `community_louvain_csv`, `speed_to_newsview_after_home`,
`home_duration_nextstate_by_decile`).

## 연산자 — 무엇끼리 재나

```
compare(분석, on=축, a=, b=, released=, ...)
decompose(비교, by=[축…])
```

두 개다. `trend` 는 **연산자가 아니라 오버뷰** — 발행하지 않고 Claude 가 서사를 쓰는 데
쓴다. `stability` 는 별도 연산자로 두지 않고 `compare` 의 출력에 포함한다.

### `compare` 가 반드시 함께 내는 것

합산 델타 하나만 내면 아래가 전부 안 보인다. 오늘 그래서 두 번 틀렸다.

| 출력 | 왜 |
|---|---|
| `pooled_delta` | 합산 델타 |
| `per_day` | **날짜별 델타 + 양쪽 물량·점유율** |
| `weight_skew` | 두 세그먼트의 날짜 가중치 어긋남 (총변동거리) |
| `dates_used` | 실제로 쓴 날짜와 **왜 그 날짜인지** |

**임계치로 막지 않고 드러낸다.** 07-24 의 델타 −79.1% 는 전이 4건짜리다. 표를 같이 내면
즉시 보이고, 숫자 하나만 내면 안 보인다.

### `compare` 의 가드

| 비교 축 | 가드 | 근거 |
|---|---|---|
| 모든 축 | **날짜 겹침 강제** | 롤아웃 때문에 안 겹치면 달력을 잰다 (+2.9% vs −0.2%) |
| `app_version` | **배포일 이전 제외** | 배포 전은 테스터 — 다른 모집단 (+2.7% vs −0.4%) |
| `period`(기간끼리) | **요일·공휴일 구성 대조** | 공휴일 한쪽 포함 시 체류 −31% 왜곡 |
| `path_ranking` | **절단된 순위 특별 취급** | 상위 200 밖은 "사라짐" 이 아니라 "컷 아래" |

### `decompose` 는 선택이 아니다

**버전 비교에는 빠져나갈 구멍이 없다.**

| 언제 비교하나 | 남는 교란 |
|---|---|
| 롤아웃 **중** | 시간대 × 버전이 얽힌다 |
| 롤아웃 **후** | 9.5.0 잔존자 = 업데이트 안 한 선택 집단 |

실측(07-27 하루, MA 안): 두 버전의 구성 차이가 `daypart` 총변동거리 **0.064**
(9.5.1 이 18~23시 +5.3%p), `os` **0.038** (android +3.8%p, iOS 롤아웃이 느림) 이었다.
성별·연령은 0.013·0.018 로 무시할 만하다.

`daypart` 가 큰 이유는 명백하다 — 롤아웃이 **하루 동안 진행 중**이라 아침 접속자는 아직
구버전, 저녁 접속자는 신버전이다. 체류·전이가 시간대에 좌우되므로 이 차이가 그대로
델타에 섞인다.

따라서 **층화 비교**가 기본이다: `decompose(compare(...), by=["daypart", "os"])` 로
층 안에서 비교하고 층별 결과를 합친다. 날짜를 맞추는 대신 **비교 가능한 층 안에서**
비교하는 것이다.

`decompose` 가 내는 것:

| 출력 | 내용 |
|---|---|
| `within` | 층 안에서의 변화분 — **이게 버전 효과 추정치다** |
| `between` | 구성 변화로 설명되는 분 |
| `per_stratum` | 층별 델타 + 양쪽 물량 |
| `composition` | 층별 비중 차이(총변동거리) — 어느 축이 얼마나 어긋났나 |

`within + between = pooled_delta` 가 성립해야 한다. 안 맞으면 분해가 틀린 것이므로
테스트로 고정한다.

> **사용량이 비슷한 날끼리 매칭하는 방식은 쓰지 않는다.** 사용량은 결과변수다.
> 버전이 사용량에 영향을 준다면 사용량으로 매칭하는 순간 효과를 지운다.
> 매칭이 필요하면 요일종류·공휴일처럼 **행동 이전의 변수**로 한다.

## 외부 달력 — 리포가 알 수 없는 사실

두 개 모두 사용자가 채우는 config 다. 없으면 조용히 틀린 답이 나온다.

| 파일 | 내용 | 없을 때 |
|---|---|---|
| `examples/config/holidays_kr.json` | 공휴일 | 검증 구간 밖 날짜를 **거부** |
| `examples/config/releases.json` | 버전 배포일 | **막지 않고** `day_volumes` 로 판단하게 함 |

둘 다 **불완전함을 파일에 명시**한다. 공휴일은 음력·대체공휴일이, 배포일은 9.5.0·9.4.x 가
아직 없다. 추측해서 채우지 않는다.

## 대시보드

- **분석을 직접 호출한다.** 세그먼트를 고르면 `analyses/` 를 불러 밀리초에 그린다.
- **그린 결과는 자동 발행된다.** 탐색하다 본 것이 그대로 공유·보관 가능해진다.
- **발행물은 파라미터에서 결정적으로 id 를 얻는다.** 같은 것을 열 번 봐도 발행물은 하나다
  (`publish_result` 의 id 가 이미 `hash(run_id, analysis_type, title)` 이다).
- **구현 기술은 정하지 않는다.** 어차피 같은 분석 함수를 부르므로 나중에 정해도 비용이
  들지 않는다.

## 마르코프 변형 — 순서가 중요하다

| 순서 | 무엇 | 왜 |
|---|---|---|
| 1 | **1차 가정 검정** | 다른 모든 지표의 전제다. `path` n=3 으로 값싸게 된다 |
| 2 | 2차 마르코프 | 1에서 깨지면 필요, 안 깨지면 불필요 |
| 3 | semi-Markov | 체류 커버리지 57~69% 한계를 명시하고 제한적으로 |
| 4 | HMM / VLMC | **지금 구조로 불가** — 큐브가 시퀀스를 집계한다. 시퀀스 캐시 설계 선행 |

**검정이 먼저다.** 2차 모델을 만들고 나서 "1차도 안 맞았네" 를 알면 그 작업이 버려진다.

## 테스트 전략

`analyses/` 는 `metrics/` 와 달리 config·파일시스템을 안다. 그래서:

- **가드 테스트가 1급이다.** 각 가드마다 "가드를 빼면 틀린 숫자가 나온다" 를 mutation
  check 로 확인한다. 오늘 이 방식이 결함 4건을 잡았다.
- **발행 왕복 테스트** — 분석 → `publish_result` → `read_result` 가 같은 프레임을 낸다.
- **봉투 필수 항목 테스트** — 커버리지·사전버전·사용날짜가 빠진 발행을 거부한다.
- 실데이터 스모크는 기존 `test_metrics_on_real_cubes.py` 패턴을 따른다.

## 구현 범위 — 한 계획서에 담을 것

이 설계 전체가 한 번에 구현되지 않는다. 첫 계획서의 범위는:

- `analytics/analyses/` 패키지와 발행 규약
- 지금 큐브로 되는 분석 **6개** (`screen_communities` 는 `networkx` 의존 때문에 마지막)
- 연산자 **2개** (`compare`, `decompose`)
- 봉투 필수 항목 강제

3단계 분석 4개(`click_distribution`·`conditional_flow`·`path_ranking`·`markov_order_test`)는
행동층 큐브가 생긴 뒤 별도 계획서다. 대시보드도 별도다.

## 이 설계가 명시적으로 하지 않는 것

- **대시보드 기술 선정** — 분석 층 완성 후
- **다중 사용자·권한** — 스펙이 "1인, 향후 소수 동료" 로 못박았다
- **실시간·스트리밍** — 큐브는 날짜별 배치다
- **새 지표 추가의 자동화** — 새 분석은 사람이 코드로 추가한다. 그게 가드가 붙는 지점이다
