# 고차 마르코프 설계 (2026-08-11)

**한 줄**: 1차 마르코프 가정이 약하다는 게 실측으로 확인됐다. **2차·3차 마르코프는 이미 빌드된
path 큐브(n=3·n=4)로 새 인프라 없이 지금 만들 수 있다.** 그 위(4차+·semi-Markov·HMM·VLMC)만
원시 시퀀스 캐시가 필요하다. 이 문서는 모델 사다리를 실측에 못박아 실행 순서를 정한다.

## 문제 — 1차는 약하다 (실측)

- `markov_order_test` 헤드라인 `excess_information` **0.504 nats** — 직전 화면을 하나 더 알면
  예측이 그만큼 나아진다(0이면 1차로 충분).
- **2026-08-11 추가 실측(2차 argmax):** ≥1,000건 문맥 169개 중 **직전 화면이 다음 화면
  예측(argmax)을 뒤집는 문맥이 59.8%, 물량으로 45.4%.** 즉 트래픽의 절반 가까이서 "현재
  화면만 보는" 1차 예측의 1순위 다음 화면이 틀린다.
- 예시(물량순): `[top/콘텐츠탭_진입] > [top/엠탑조회]` 3억 87만 건 — 1차는 다음을 `엠탑조회`
  자기루프로 보지만 2차 관측은 `media/m_newsview_보기`. `[top/홈탭_진입] > [media/뉴스보기]`
  1억 34만 건 — 1차 `엠탑조회`, 2차 `홈탭_진입`. 직전 화면이 진행 방향을 바꾼다.

## 모델 사다리 — 필요 데이터 vs 현재 큐브

| 모델 | 필요한 것 | 현재 큐브가 주나 | 판정 |
|---|---|---|---|
| **2차 마르코프** | `P(next \| prev, cur)` = (prev,cur,next) 카운트 | **path n=3** (coverage **0.983**) | **지금 가능** |
| **3차 마르코프** | (p2,p1,cur,next) 카운트 | **path n=4** (coverage **0.896**) | **지금 가능**(꼬리 10% 명시) |
| 4차+ | path n=5 coverage **0.769**, 더 깊으면 더 하락 | 상위200 컷이 물어 coverage 하락 | 시퀀스 캐시 |
| semi-Markov | 방문 단위 **체류 분포**(체류가 다음 화면·이탈을 좌우) | 큐브가 체류를 이미 합침 — 없음 | **보류**(gap④ 삭제 맥락, 아래) |
| HMM | 원시 시퀀스로 EM(은닉 상태 추정) | 없음 | 시퀀스 캐시 |
| VLMC | 원시 시퀀스로 문맥을 데이터가 정하는 길이만큼 성장 | 없음 | 시퀀스 캐시 |

**왜 path 큐브로 2차가 되나:** path 큐브는 세그먼트별 n-gram 카운트다. n=3 행 `(s1,s2,s3, cnt)`
를 세그먼트 합산하면 `P(s3 | s1,s2) = cnt(s1,s2,s3) / Σ_x cnt(s1,s2,x)` 가 바로 2차 전이확률이다.
`markov_order_test` 가 이미 이 분포를 만들어(파일 `analytics/analyses/paths.py::_parse_trigrams`)
1차와 KL 로 견주기만 한다 — **모델로 노출만 안 했을 뿐 계산은 이미 있다.**

## 즉시 실행 (인프라 불필요) — 2차·3차 분석

**새 분석 `markov_order_flow`**(가칭), 파라미터 `order ∈ {2, 3}`:

- 상태 = 직전 `order−1` 개 화면의 튜플. path n=`order+1` 큐브에서 `P(next | 문맥)` 산출.
- 헤드라인/프레임:
  1. **직전-의존 핫스팟 순위** — argmax 가 1차와 달라지는 문맥을 물량순으로(위 실측 표가 그대로
     프레임이 된다). "어디서 직전 화면을 봐야 하는가" 를 답한다.
  2. **차수별 예측 이득** — `excess_information`(2차) vs 3차 추가 이득. 사다리를 어디서 멈출지 근거.
  3. **2차 이탈·엔트로피** — 문맥별 다음 화면 엔트로피, 이탈확률(EXIT 로의 2차 전이).
- 재사용: `_parse_trigrams`·`_one_n`(paths.py), 1차 예측은 전이 큐브(markov_order_test 와 동일 경로).
- **세그먼트 합산 함정**(재확인): path 큐브는 rollup 행이 없어 세그먼트별로 쪼개져 있다 — 관측
  분포 전에 `(문맥,next)` 로 반드시 합산한다(안 하면 조각 확률로 KL 음수). markov_order_test 가
  이미 밟고 고친 함정. mutation check 로 합산 가드를 되주입해 검증한다.
- coverage(0.983/0.896)를 봉투에 싣는다 — 상위200 컷 밖 경로엔 성립 안 함을 명시.

## 인프라 필요 — 세션 시퀀스 캐시 (HMM·VLMC·4차+)

top-200 컷 없이 임의 차수/가변 문맥/EM 을 하려면 원시 시퀀스가 있어야 한다. 실측(react-migration
메모리, `scratchpad/{seq_test,duckdb_ngram_test}.py`):

- **추출**: 세션별 화면순서 array (`array_agg`, 조인 없음) → Trino stuck 사라짐, ~55분·**2.6GB/일**.
- **저장**: `cache/sequences/{sql_hash}/date=YYYY-MM-DD.parquet` — 기존 큐브 규약(sql_hash·날짜 파티션)
  그대로. 조회는 선택 기간만 로드.
- **연산**: pandas 통째 로드는 13.9GB/일로 나쁨 → **DuckDB 로 parquet 직접** n-gram/EM
  (memory_limit 캡, 5.6GB·12분, 경로수 pandas 와 정확 일치). cube_store 는 **작은 집계 결과**만 상주.
- 이 캐시 위에서: 임의 n n-gram(컷 없음), **VLMC**(문맥을 데이터가 정하는 길이로), **HMM**(EM).

## 권장 순서

1. **2차 분석 구현**(즉시, TDD) — 물량 45%가 걸린 값. path n=3, 새 인프라 0.
2. **3차**(n=4, 꼬리 10% 봉투 명시) — 2차가 부족한 문맥에서 얼마나 더 주는지.
3. **[평가 게이트]** 2·3차 예측 이득을 재고, 시퀀스 캐시(추출 55분/일 × 22일 + DuckDB 파이프라인)
   비용을 감수할 만큼 4차+/VLMC 가 더 주는지 **측정 후 결정**. 안 주면 여기서 멈춘다.
4. 시퀀스 캐시 → **VLMC**(가변 차수가 고정 차수보다 데이터에 정직) → **HMM**(은닉 상태 필요 시).
5. **semi-Markov 는 보류**: 체류 분포가 필요한데 그건 gap④(체류 십분위 × 다음 화면)와 같은 벽이고,
   **gap④ 는 2026-08-11 삭제 결정**이다. 시퀀스 캐시에 방문 단위 체류를 함께 실으면 나중에 열리나,
   지금 우선순위 아님.

## 재조사 불필요한 실측 (2026-08-11)

- path coverage(상위200이 덮는 n-window 비율): **n=3 0.983 · n=4 0.896 · n=5 0.769**.
- 2차 argmax flip: ≥1,000건 문맥 **169개 중 101개(59.8%)**, **물량 45.4%** 에서 1차 argmax 가 틀림.
- 2차 전이확률은 path n=3 를 `(prev,cur,next)` 합산해 행정규화하면 나온다 — `markov_order_test`
  가 이미 그 분포를 만든다. **새 쿼리·재빌드 불필요.**
- 측정 스크립트: `scratchpad/markov2_feasibility.py`.
