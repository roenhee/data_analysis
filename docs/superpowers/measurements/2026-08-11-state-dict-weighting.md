# state 사전 채택 가중치 — 행수 vs 세션 vs 유저 (2026-08-11)

**질문(로드맵 미결 ①):** state 사전 채택이 `count(*)`(이벤트 행 수) 가중이라 봇/반복이 상위
화면을 왜곡하지 않나. → **측정으로 재정의:** "봇 노출"보다 **반복-가중이 소규모 서비스를 굶기는
것**이 실질 문제다. 세션 가중으로 바꾸면 완화된다.

## 현재 코드

- `analytics/cube/state_sql.py::_count_sql` = `SELECT value, count(*) AS cnt ... GROUP BY value`.
  화면 값 = `c_service_code || '/' || action.name`, 필터 `action.type='Pageview'`.
- `BASE_FILTERS` 에 **`coalesce(tag.is_invalid,'0') <> '1'`** 있음 → **플래그된 봇은 이미 제외.**
- `apply_cut`: cnt 내림차순 누적 95% + min 10,000 채택.
- 즉 남는 위험은 "플래그 안 된 고빈도 반복"(허브 재방문·미플래그 스크레이퍼)이 **행 수**로
  채택을 좌우하는 것.

## 측정 (1일 2026-07-20, 7서비스, 누적95%·min10k)

화면 158개에 대해 `count(*)` vs `approx_distinct(session)` vs `approx_distinct(user)` 로 각각 컷:

| 가중 | 채택 수 | rows 대비 |
|---|---|---|
| `count(*)` 행수(현재) | **10** | — |
| 고유 세션 | **11** | `top/검색창엔트리_진입` 추가 |
| 고유 유저 | **13** | + `sports/p_newsview_보기`·`sports/pv` 추가 |

- **`rows ⊆ sessions ⊆ users`** — 세션/유저 가중은 행수 채택분을 **하나도 버리지 않고 더 넓게**
  채택한다(`rows − sessions = ∅`). 방향이 명확: 세션 가중 = **커버리지 확대**.
- 세션/유저가 추가하는 화면은 정확히 **소규모 서비스**(sports) 것 — 로드맵의 "사전이 작은
  서비스를 굶긴다"(sports 37%·entertain 19% /other) 문제와 **같은 뿌리**.
- 행수 부풀림 상위(≥100만행, 세션당 반복): `top/다음_PC탑` **9.8**·`top/엠탑조회` **7.3**·
  `media/p_newsview_보기` **6.3** 회/세션. **이건 봇이 아니라 허브 화면 재방문**(정상 행동).
  → "봇 노출" 프레임은 부정확. 실효는 **반복-가중이 허브를 키우고 얕고 넓은 화면을 죽이는 것**.

## 판단

**권장: 사전 채택을 `count(*)` → `approx_distinct(session)` 로 바꾼다.**

- **왜 세션**: (1) 반복/파워유저/미플래그 봇 부풀림을 감쇠(세션당 여러 번=1). (2) 커버리지가
  **넓어져** 소규모 서비스 화면이 사전에 들어와 /other 굶주림 완화. (3) 플랫폼 분석 단위가
  세션(`(uuid,suid)`)이라 개념적으로 정합. (4) `approx_distinct` 는 Trino 에서 싸다.
- **유저 가중**은 더 넓히나(13) 세션이 더 자연스러운 단위(세션 기반 플랫폼). 유저는 "몇 명이
  봤나"라 재방문 잦은 실사용 화면을 과소평가할 수 있다.
- **비용**: 사전이 바뀌면 `state_dict_version` 이 바뀌고 → 모든 큐브 `sql_hash` 가 바뀐다
  → **7서비스 22일 전량 재빌드**(≈수 시간, `build_loop_v2` 로 자동재시도). 이게 유일한 진짜 비용.
- **대안(재빌드 없음, 약함)**: 사전은 그대로 두고 품질 봉투에 화면별 `rows/sessions` 비를 실어
  "반복 부풀림" 을 드러내기만. /other 굶주림은 **못 고침**. 근본 해결 아님.

## 결정 (2026-08-11) — SQL 은 바꾸되 재빌드는 생략

`_count_sql` 을 `count(*)` → **`approx_distinct(user.uuid || '|' || user.suid)`** 로 바꿨다
(state_sql.py). **향후 어떤 빌드든 세션 가중을 쓴다** — 원칙적으로 옳고, is_invalid 이후 남는
반복 편향을 없앤다.

**하지만 지금 전량 재빌드는 하지 않는다.** 22일 창으로 새 세션 가중 사전을 실제로 지어 보니
(`sd_e9e2447e3b16953a`) **11화면 — 기존 10화면과의 차이는 `top/검색창엔트리_진입` 단 하나**
(그것도 top 서비스). sports 등 소규모 서비스 화면은 이미 기존 사전에 있었다. 즉 **행수 vs 세션
가중 왜곡이 이 데이터에선 실질적으로 +1 화면뿐**이라, 22일×7서비스×6큐브 전량 재빌드(다중 시간
Trino, stuck 취약, 이후 실큐브 골든값 연쇄 재보정)를 정당화하지 못한다. **사용자 결정: 재빌드 생략.**

- 서빙은 계속 기존 정본 `sd_68461a6e4fc6ccac`(rows 가중, 10화면)로 돈다 — meta 상수 안 바꿈.
- 다음에 어떤 이유로든 큐브를 새로 지으면 그때 세션 가중 사전(sd_e9e2447e3b16953a 계열)이
  자동 적용된다. 그 시점에 실큐브 골든값 재보정 + meta 전환을 함께 한다.
- 교훈: **#4 "봇 노출" 우려는 이 데이터에선 대체로 이론적**이었다(is_invalid 필터 + 세션 가중
  차이가 +1 화면). 측정이 재빌드 수 시간을 아꼈다.
